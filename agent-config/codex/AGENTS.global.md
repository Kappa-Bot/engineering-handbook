# Kappa-Bot Engineering Global Instructions

Canonical engineering source: MelodIQ Mindset (the repository historically located at `Kappa-Bot/engineering-handbook`). The `engineering-handbook` managed router and manifest identity are compatibility contracts. Use the explicitly verified repository locator for manual updates.

The Engineering Handbook governs all engineering/repository work. Keep this file small: trivial local work may be decided by this baseline plus repo-local authority, while specialized procedures belong in focused handbook artifacts loaded only when relevant.

- Handbook updates and checks are **manual-only in every coding-agent harness**, not just Codex. No lifecycle, prompt, model, tool, subagent, stop, retry, workspace-open, plugin or MCP hook may fetch, verify, refresh or block a run on the Handbook's behalf. The root/master parent uses already-installed canonical knowledge and repo-local authority; invoke `doctor`/`preflight` or explicit `install` only when the user directs an update or a scoped engineering task requires deliberate verification. Share the chosen local snapshot with delegates without changing it mid-execution. If local information is stale or unverifiable, say so instead of blocking conversation or claiming compliance. Never update consumer checkouts, overwrite custom global instructions or bypass candidate integrity checks on an explicit update.
- `STALE_OFFLINE` is a verified last-known-good copy, not current-remote evidence. Use `search`, `tree`, `explain` and `doctor` for discovery; an unmatched classifier, unresolved path or empty risk set is not a safety PASS.

- Keep scope narrow. No unrelated refactors, abstractions, or cleanup.
- For writing, renaming, cleaning or organizing code, use `std-code-quality-organization-baseline` and `pb-code-change-workflow`: follow local naming/folder/toolchain conventions, trace affected consumers and public contracts, preserve explicit errors and test the relevant behavior. For library selection, `std-dependency-supply-chain-baseline` remains the authority; evaluating a library never implies permission to install it.
- For holistic or focused quality reviews (UX, UI, accessibility, performance, security, privacy, reliability), enter through `pb-engineering-quality-audit` and follow detected domain owners; use `std-privacy-data-handling-baseline` for personal-data lifecycles beyond public websites. Pin the actual repo/revision and journeys, inspect real owner/config/test paths and select risk-specific proof. An audit is read-only and does not authorize automatic fixes, Unslop redesign, load tests, issue publication, migrations, deploys or provider spending; unrun gates stay unrun.
- Reuse first: current repo → handbook → relevant mature internal assets/repos → mature external solutions → new design.
- Treat the handbook as the canonical baseline, not a ceiling: for new transversal or quality-sensitive work, compare relevant mature internal implementations when that can materially improve the result.
- Keep capabilities truthful across local/demo/Preview/QA/Production. Do not simulate unavailable persistence, security, deployment, offline or integration behavior.
- Use zero spawned workers by default; spawn only when the user expressly requests delegation or applicable repo/skill instructions request it. Route authorized delegation: deterministic tool/script → direct controller execution → one Agency Agents specialist → second independent specialist only for distinct parallel value or a required review boundary.
- Agency Agents is the upstream specialist-persona catalog. A matching persona is not itself a reason to spawn; use `std-agent-runtime-routing`, `pb-agent-runtime-routing` and `ref-agency-agents-specialist-routing`.
- Do not use fixed `parent/design-quality/delivery` identities or bind models to job titles. Specialist persona, model and reasoning effort are separate runtime decisions.
- Use quality-first task routing: Sol 6.2/high for substantive engineering; Sol/xhigh for complex integration; Astra 6.2/high–xhigh for demanding security/architecture/data reasoning; Terra 6.1/high for frozen bounded work and supported visual/browser work. Never select GPT-6 Luna, including fallback. If Terra is observably unavailable, use the Standard's available Sol fallback. `max` requires specific evidence, not a routine preset.
- Every spawn sets both model and reasoning effort explicitly when supported. Resolve the actual client/allowlist and native custom-agent TOML overrides (which can take precedence over spawn settings); record requested/actual values instead of silently substituting. An API model listing does not prove Codex CLI/app/IDE availability.
- Independent model review is risk-triggered, not universal. Strong deterministic tests + diff inspection can close low/medium-risk work; security/authz/tenant isolation, durable-data migration, money, consequential Production/provider actions, costly external contracts, partial concurrency proof or high-impact weakly-verifiable architecture require independent review.
- Escalate by cause, not by automatic model retry ladders: fix environment failures, resolve authority ambiguity, let the same worker fix clear defects, change method/specialist for repeated bad hypotheses, and increase capability/effort only for actual reasoning insufficiency.
- Keep routine concurrency at zero/one and at most two spawned workers concurrently unless the owner explicitly authorizes a different limit. No nested spawning by default; controller owns integration and final claims.
- Do not treat increased reasoning/token budget as authorization for extra monetary charges, paid tiers, new providers or GitHub Actions. Give workers sufficient context and review time within included usage; never reduce the verification floor merely to minimize tokens.
- When the owner authorizes exhaustive zero-cost execution, continue dependency-ready authorized work through checkpoints while respecting actual runtime, mandatory evidence, sensitive-action authority and monetary limits.
- Use one normal working tree by default. Do not create Git worktrees unless explicitly requested or real same-repo parallelism clearly justifies one.
- Preserve unmerged and user work. Never use destructive cleanup merely to simplify the workspace.
- For actively managed Kappa-Bot project repos, `main` is the default persistent product branch. Feature/release/docs branches are temporary source-control tools and must be resolved/deleted after integration or initiative closure without destroying unique work. Do not create or preserve a `qa`/`staging` branch as an environment boundary unless the owner explicitly approves that exception.
- For Supabase database topology, apply the owner-authorization boundary in [Supabase database branches](#supabase-database-branches) below; Git branches and QA/Preview requests never imply database-branch permission.
- Keep transient scratch/review files outside the repo when practical.
- Plan proportionally before non-trivial implementation; keep mechanical work lightweight.
- Keep research, decision, spec, plan, implementation, verification and adoption distinct when the distinction matters.
- Do not silently expand scope.
- Never claim a gate passed unless it was actually executed and observed.
- Distinguish source/build checks from deployment, migration, runtime, visual and native-device evidence.
- For local SQL/integration verification, follow `std-testing-release-quality-baseline` section 3A: at most one minimal reusable local PostgreSQL container per product/vertical, no duplicates/replicas/replacements/sidecars, and mandatory stop after testing. Do not weaken blocked SQL evidence.
- Treat CI and repository automation as metered infrastructure: keep automatic push/PR hot paths small, non-duplicative and timeout-bounded; run expensive build/DB/browser/visual/remote gates only at the cadence their distinct risk requires, and measure real workflow timing after material changes.
- Tests, scripts, docs, workflows, fixtures and generated artifacts need current consumers; merge or remove obsolete machinery instead of keeping implementation history alive in the working repository.
- Never surface raw backend/transport/provider diagnostics as ordinary user-facing product copy; preserve technical detail in appropriate internal observability and present users with human recovery-oriented messages.
- Prefer small, reviewable changes and an explicit handoff.
- Load repo-local `AGENTS.md` and only specialized handbook material required for the task; minimize permanent context and duplicated instructions.
- For non-trivial work, use the single generic `engineering-handbook` router and its deterministic context capsule/delta flow when available; trivial work remains governed by the handbook without requiring a full context query when the baseline and local instructions already decide it.
- For material user-facing UI work, use the integrated Unslop method in `std-ui-ux-quality-baseline`, `pat-design-context-layering` and `pb-frontend-quality-review`: diagnosis, product direction, nine-pass dispositions and real rendered acceptance. Missing required render evidence means incomplete acceptance, not PASS.
- In an authorized redesign, reconstruct systemic slop and supersede weak legacy composition/tokens; prior approval is not permanent protection. Keep product truth, capabilities, access and release boundaries. Resolve `pat-visual-direction-catalog`: **Glassmorphism starts as the default only for new/authorized internal-console material design lacking a current local choice**, with selectable Neumorphism/solid alternatives; shell mechanics (`pat-operator-console-shell-interactions`) and public heroes have no defaults. An audit or micro-edit is not redesign authority; do not install a runtime style picker.
- Use supplemental design/interaction skills only when they materially improve the integrated method. Do not install a second Unslop router or invoke a full design-skill stack performatively. Apply PWA guidance only to actual PWA scope.
- For substantial agentic execution, use only the planning/TDD/debugging/verification/review methods required by the stage/risk. `/caveman Ultra` is optional when installed and useful; no process-skill suite is the specialist-agent taxonomy.
- Discover actual MCP/CLI availability, authentication and permissions; prefer available `playwright-cli` for suitable browser exploration while retaining the repo's required test gates. Avoid duplicate tool actions and load only relevant resources under the Standard's cost controls.
- For material architecture/data/security/release/production changes, apply the corresponding handbook baseline and keep provider/tool choices contextual.
- Generated handbook capsules never override canonical Markdown or permitted repo-local decisions.
- Reconcile active consumer routing and installed projections through existing adoption/sync procedures; a Handbook commit is not proof that a workstation or live model was updated. Refresh/reconcile Agency Agents at safe boundaries, record material upstream revision/runtime routing, and do not equate an Agency Agents app binary update with persona reconciliation. Preserve unrelated local settings and historical evidence.
- Do not create domain-specific skills to duplicate the handbook.

## Supabase database branches

**Edgard's explicit prior authorization is required to create any Supabase database branch.** Record the exact project, branch, purpose, scope, lifecycle and cost boundary. The guard covers free, included-quota, paid and temporary branches, including creation triggered by integrations or automation. Check Git and Preview side effects. Stop the operation if unauthorized branch creation cannot be ruled out. Persistent paid remote database topology defaults to **Production only**. Read the Supabase database branches section of `references/policies/agent-operating-model.md` in the selected installed Handbook skill or `policies/agent-operating-model.md` in the selected checkout.
